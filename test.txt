olygon meshes; >Most commonly used geometric modeling technique<br> >Explicit representation by defining surfaces explicitly<br> >Extension/continuation of point cloud (simple discrete points) by listing not only points (polygon vertex coordinates) but also connections between vertices to form polygons<br> >First need to decide what shape (polyg) to use: triangle, quadrilateral, pentagon, hexagon, etc;  

Triangle meshes; >1st polyg mesh: Stanford bunny (its a triangle mesh)<br> >When u zoom into surface, each patch is a small triangle<br> >Possible to make polyg mesh w any polyg/shape, but most meshes r triangle meshes<br> >Most simple polyg<br> >Any polg can b decomposed into a bunch of triangle primitives, no matter how complex og polyg is<br> >So we can represent any shape using triangles<br> >Triangles r convex <- v nice property. Makes things simpler during algo implementation so u wouldnt need to program a case if its convex and a case if its nonconvex, u know for sure all cases r convex<br> >Simple algos for stuff further down pipeline like rasterization, interpolation<br> >Easy to optimize simplicity<br> >We r mostly focused on processing triangle meshes;  

Convexity; >If u draw 2 points that r contained within the shape and connect the 2 points with a line, is the line guaranteed to be within the shape still?<br> >True for ALL triangles no matter vertices arrangement<br> >True for some quadrilaterals (ex squares) but not all -> if u move vertices u can get a nonconvex quadrilateral;  

Triangle soup; >Simple way to represent/store triangles<br> >Point cloud but for triangles: store 3 vertices per triangle <- triangle implied by each vertex triplet<br> >So just a giant list of triplets [(x0,y0,z0),(x1,y1,z1),(x2,y2,z2), (x0,y0,z0),(x3,y3,z3),(x1,y1,z1)]<br> >Assuming every 3 consecutive vertex/triplet forms 1 triangle<br> >Can store more than just xyz coords, can store colour etc<br> >Inefficient: if triangles share a vertex, its stored multiple times<br> >Simple operations on complex meshes (ex 1 mil triangles) may b super expensive<br> >Ex: finding all triangles that share a vertex w a given triangle - need to iterate thru every single triangle in giant list;  

“vertex list” + “face list”; >Use level of indirection -> instead of directly using vertices, refer to them by their indices<br> >Basically use a wrapper<br> >U have 2 big lists: list of all vertices (so a point cloud basically) and a list of triangles (via the indices of the 1st list)<br> >Vertex list<br> [(x0,y0,z0), (x1,y1,z1), (x2,y2,z2), (x3,y3,z3)]<br> >Face list<br> [(0,1,2), (0,3,1)]<br> >Now u get rid of a lot of the redundancy since all ur repeating r the indices<br> >However many common, important operations still difficult, again finding common vertices for instance;  

topology vs geometry; >Topology: local structure, does not care about actual coordinates. Only the indv connections between vertices, how many triangles share a vertex, etc<br> >Geometry: care about global structure (in addition to local structure), so how the entire mesh looks as a whole<br> >Mesh can have same topology diff vertices -> so all the connections r the same even tho the vertices r placed in diff locations. Kinda like isomorphic graph. So this one is same topologically but diff geometrically<br> >If Different topology, same vertices “shape” may look the same but its diff tolopogically and geometrically<br> >Topology matters more than geometry. So we should optimize data structure to focus more on that (topologic connections) 2 make mesh connections easier;  

Half edge data structure; >Split each edge lengthwise<br> >Stores lots of info abt adjacent faces/vertices/edges<br> >AKA “doubly connected edge list” (uses pointers like a linked list)<br> >Basically a directed graph with pointers to a lot of places. Seems like a lot of pointers but all these do have some use!<br> >Right hand rule: assume all edges go around triangle counter clockwise<br> >Halfedge {<br> >Halfedge* pair;<br> >Halfedge* next;<br> >Halfedge* prev;<br> >Face* left;<br> >Vertex* origin;<br> >Edge* edge;<br> >}<br> >Vertex { Halfedge* half; }<br> >Edge { Halfedge* half; }<br> >Face { Halfedge* half; }<br> >Notice how these all only need 1 pointer -> intentional! Bc halfedges store so much info, great property is that we basically can store variable info w a constant amt of edges<br> >Efficient operations like adjac traversals<br> >Diff implementations handle outer triangles diff. For instance u can have the pair be null or face pointer 2 b null<br> >Not storing any coords, just pointers to other half edges<br> >We arent focusing on constructing the actual triangulation (needs scanner or artist to create model) we r just assuming we have all the data alr, need a way to efficiently store and process data;  

Traversal w half edges; >pair, next, and prev pointers make it easy to traverse the mesh, and pull out elements using origin, edge, or left pointers<br> >Can quickly get info like which edges r connected to same vertex;  

Traversing edges around a vertex; >Halfedge* h = vertex.half;<br> >do {<br> // do something with h.edge<br> h = h.pair.next;<br> } while (h != vertex.half)<br> >Kinda like LL traversal;  

Traversing edges around a triangle; >Halfedge* h = face.half;<br> >do {<br> // do something with h.edge<br> h = h.next;<br> } while (h != face.half)<br> >Being able to retrieve all edges forming a triangle easily and only needing to store 1 half edge for that triangle<br> >Can choose any edge (arbitrary) and itll still work<br> >Can do many more complex things like finding shortest path;
