Raytracing; Raytracing is more ___ than rasterization<br> More faithful than rasterization (takes a shortcut by directly projecting)<br> Raytracing actually tries to simulate the light rays’ path - scattering, reflecting, etc. good for realism<br> Rasterization less expensive bc when we project obj onto 2d plane, chances r it wont cover every single pixel so we can effectively ignore some. Whereas for raytracing we need 2 loop thru every pixel<br> Rasterization a lot faster;  
Basic idea behind ray direction in raycasting/tracing; How cameras work irl is capturing all the light bounces at it in a scene (that hits its lens)<br> Many many possible paths for the light photons to take (rays in our abstraction) and irl most of the light is just There lol<br> Naive way is to simulate all light rays in scene, but most of that compute power is wasted bc most of those light rays dont hit ur camera lens so it doesnt actually contribute to the end img<br> Key idea: reverse -> cast rays starting from camera into scene, instead of going from light source and tyring to figure out which just ~happen~ to hit the camera<br> Each ray cast from the camera that hits teh obj is tracing out a path for which light can go from light source to reflect off the obj and into the camera lens<br> Basically if obj intersects w the ray it can be visible to the camera<br> No set amt of rays u should cast, the more the better tho. So u want enough that u get a good img;  
Raycasting; Rays r a simplified way to check whats visible from cameras POV<br> Works for any shape, but in practice a lot of the objs r triangles (since triangle meshes r super common);  
The ray casting algorithm; Algorithm: “For each ray, find closest object it hits”<br> for pixel sample point p (some pixel on 2d img plane)<br> r = ray(o,p); // ray from camera origin o through p<br> r.min_t = infinity; r.obj = null;<br> for object obj {<br> if (r.intersects(obj)) { // ray-object intersection<br> if (r.distance(obj) < r.min_t)<br> r.min_t = r.distance(obj); r.obj = obj<br> }<br> }<br> If ray misses obj no operations perform<br> After all objs r looped thru, just return nearest obj and we colour in the pixel in the colour of obj<br> Looping thru all objs (the triangle meshes that make up the greater obj/polyg mesh) can b incredibly expensive bc for complex scenes there can b millions or bills or triangles<br> (can use spacial accel to speed up);  
Constructing rays; • Parametric equation for ray<br> r(𝑡) = o + 𝑡d<br> • Origin o at camera position, direction vector d<br> • If d is normalized (unit length), 𝑡 is distance along ray<br> • How to get d ? Line between camera origin o and position through pixel on image plane p<br> d is xyz while t is just a scalar;  
Ray intersection tests; Can b performed on any shape<br> But since most meshes use triangles, mostly we care abt the triangles;  
Ray-sphere intersection; For simplicity, we r considering example w sphere;  
Raytracing: recursive raycasting; Raycasting except u need to perform it a bunch of times to see if camera can actually sense the obj and if light illuminates the obj<br> Basically trying to construct a path from light source to pixel (camera pos)<br> Allows simulation of pretty complex light interactions in scene like reflections, transparency<br> First cast ray from camera to obj, then at intersection point try to cast a path to light source to simulate if photon can bounce from light source off obj into camera<br> If path exists, direct light -> u know u can colour pixel brighter<br> If no dir path -> snth is blocking the light, so it can b darker<br> elegantly simple, but expensive!<br> Short code, easy to implement for high-fidelity rendering<br> • Algorithm of choice for visual effects in movies, “pre-rendered” content, offline where u can spend a lot of time b4hand. So not high performance real time apps;  
Computational challenge of ray tracing; bounce-> rays cast from intersection pts that intersect at other objs. Then u cast another ray from this new intersection pt. Mb it intersects w a diff obj, mb with the light source<br> So u end up with very complex paths which bounce off multiple objs before hitting light source (so it simulates how light can reflect off objs that reflect off other objs and then we see it)<br> Recursively bounce as many times as u want, the more bounces the more realistic<br> Very high computational cost: every light ray that bounces spawns even more rays. So num of rays we gotta cast grows exponentially<br> Multiple rays can b cast per pixel;  
Single v multiple bounces; More bounces = more realistic<br> If its just single bounce, if obj doesnt have direct illumination its game over and it just looks super dark/shadowed<br> But how stuff works irl is light bounces so even areas w/o direct illumination dont seem like ~shadow~<br> So overall the scene is a lot brighter and visible;  
Light paths r also complex; Irl light sources arent just one (1) pixel! So simulating say light panels requires casting rays in multiple diff dirs and seeing which hit the panel (not just the pixel) -> light sources w large SA create softer shadows compared to hard shadows if light source is smaller<br> Transparent objs can bend light rays<br> Indirect illumination where light bounces everywhere creates wacky paths that arent just source->obj. Makes scene more bright<br> Realistic scene rendering requires simulation of all these complex light paths<br> At some point the amt of light that can travel along that path u can just ignore the rest of the path<br> The first few bounces have the most contribution as the light is strongest then;  
Computational tradeoffs: rasterization vs ray tracing; Rasterization: loop over triangles first<br> • Never have to store entire scene, supports unbounded size scenes<br> • Store depth buffer (need random access to regular structure of fixed size)<br> • Hard to model complex interactions (reflection, refraction, etc.)<br> Ray casting: loop over pixels/rays first<br> • Never have to store closest depth for entire screen (just current ray)<br> • Natural order for rendering transparent surfaces (process surfaces in the order they are encountered along the ray: front-to-back or back-to-front)<br> • Must store entire scene (random access to irregular structure of variable size: depends on complexity and distribution of scene)<br> Naive implementation requires us to check every ray against every obj;
